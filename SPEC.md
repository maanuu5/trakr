# Trakr — build specification

**How to use this document:** paste this whole file to your coding agent as the first message, or drop it in the repo root as `SPEC.md`. Self-contained.

## 1. What this is

Most Discord servers run a handful of bots — moderation, music, leveling, welcome messages — and nobody watches any of them. Trakr is an SRE dashboard for the other bots already running in your server: which ones are actually online, which ones have gone quiet, and which moderation bot did what and when. Every number comes directly from a fact Discord's own API hands over — presence state, posted messages, audit log entries — nothing inferred, nothing guessed. All of it lives in **SigNoz**, self-hosted, which is what's being judged.

Built for **Agents of SigNoz** (WeMakeDevs × SigNoz), July 20–26, 2026, Track 3 (Build Your Own).

**Definition of done:** a fresh clone, with Docker Desktop running, stands up SigNoz with one command and the observer bot with another. Left running against a real server for a few days, it produces an uptime leaderboard, an activity dashboard, a moderation-action log, a recovery funnel, three test-fired alerts, and a working MCP query — all backed by real Discord events, none of it faked for the demo.

## 3. Architecture at a glance

```
Discord Gateway (presence + message events)  ─┐
Discord Audit Log API (polled every 2 min)    ─┼─► observer bot ─► SigNoz ─► dashboards, funnel, alerts
                                                                        │
                                                                   MCP server
                                                                        │
                                                     ask: "which bot's flakiest this week"
```

One small always-running Python process, one Discord bot token, no other bots involved or modified — it just watches.

## 4. Tech stack

Python, `discord.py` (mature, well-documented, handles gateway reconnection for you), OpenTelemetry Python SDK exporting to SigNoz. SQLite for local state (tracking when each bot last went offline, so downtime duration is computable when it comes back). SigNoz self-hosted via Foundry (`mode: docker`, `flavor: compose`) — same as every other plan in this conversation, never tool-specific.

## 6. Getting started — do this before July 20

1. **Install Docker Desktop**, enable WSL2, bump memory to 4–8GB in Settings → Resources.
2. **Install Foundry**, deploy SigNoz locally (`foundryctl cast -f casting.yaml`), confirm the UI loads at `localhost:8080`.
3. **Create the Discord bot application** (§8) — free, takes five minutes, nothing to pay for ever.
4. **Pick or set up a test server** you administrate, with at least one or two other bots already in it (a music bot, a mod bot, whatever you've already got — the more real bots in there, the better the eventual demo).
5. Don't write `bot.py` or anything else yet. Setup only, until the 20th.

**Worth doing early, unlike the other projects in this conversation:** once your bot token exists and intents are enabled, there's no reason not to get the bot connected and idling in your server *before* the 20th, purely to start accumulating real presence/activity history. More real days of data behind it makes the eventual demo more convincing than a dashboard that only has an hour of history. Connecting it and leaving it running is setup, not "the project" — writing the OTel export logic is what waits for the 20th.

## 8. Discord bot setup

1. Go to the Discord Developer Portal → New Application → name it (e.g. "Trakr").
2. Bot tab → Reset Token, copy it, treat it like a password (env variable, never committed).
3. Same Bot tab → Privileged Gateway Intents → enable **Presence Intent** and **Server Members Intent**. For a bot in under 100 servers (yours), this is a self-service toggle, no Discord review needed.
4. OAuth2 → URL Generator → scope `bot`, permissions: `View Channels`, `Read Message History`, `View Audit Log`. Deliberately minimal — this bot only watches, it never needs to post, moderate, or manage anything.
5. Use the generated URL to invite it to your test server.

## 9. The observer bot

`observer/bot.py` — a `discord.py` client with `intents.presences = True`, `intents.members = True` (message content intent is *not* needed unless you want to log the literal text of what bots post, which is optional — knowing *that* and *when* a bot posted is enough for the core build).

**On presence update:** if the user isn't a bot, ignore. If `before.status` and `after.status` differ, this is a real state change: set the `trakr.bot.online` gauge (1 or 0), emit a log line, and update SQLite. If the bot just went offline, record the timestamp. If it just came back online, compute the gap against the stored offline timestamp and record it as downtime duration — this is where the "how long was it actually down" number comes from, computed, not guessed.

**On message:** if the author isn't a bot, or is this bot itself, ignore. Otherwise increment the message counter, tagged by which bot posted and which channel, and emit a correlated log.

**Audit log polling** (`audit_poll.py`, a `discord.ext.tasks` loop every 2 minutes): fetch audit log entries since the last poll; for each one where the acting user is a bot, increment the moderation-action counter tagged by bot and action type (ban, kick, timeout, etc.), and emit a log. Store the last-checked timestamp in SQLite so a restart doesn't re-process old entries.

Wrap all three handlers in try/except with `record_exception` — a bug here should never crash the whole observer.

## 10. Data schema

**Resource:** `service.name = "trakr"`.

**Metrics:**

| Metric | Type | Attributes |
|---|---|---|
| `trakr.bot.online` | Gauge (0/1) | `bot.name`, `bot.id` |
| `trakr.bot.messages` | Counter | `bot.name`, `bot.id`, `channel` |
| `trakr.bot.mod_actions` | Counter | `bot.name`, `bot.id`, `action_type` |
| `trakr.bot.downtime_seconds` | Histogram | `bot.name`, `bot.id` — recorded when a bot comes back online |

**Logs:** one per event (presence change, message, mod action), human-readable body (e.g. `"MusicBot went offline"`, `"ModBot banned user #1234"`), attributes matching the metric dimensions.

**Exceptions:** wrap the bot's own event handlers so a crash produces a real exception in SigNoz, not silent downtime in the observer itself.

## 11. SigNoz build list

- **Uptime & Reliability** — gauge history per bot gives uptime % over any window for free; a leaderboard table ranking bots by uptime; a timeline of downtime events.
- **Activity** — messages-per-bot over time; a ranking of most to least active; a "gone quiet" view — a bot whose message rate drops sharply below its own rolling average, a real anomaly-detection candidate.
- **Moderation** — mod actions per bot, broken down by action type, over time.
- **Funnel — recovery:** bot goes offline → bot comes back online → bot posts its first message after recovery. Distinguishes bots that fully recover from ones that reconnect to Discord but never actually resume working — a real, meaningful distinction a simple uptime number would miss.
- **Alerts:** (1) threshold — a bot's online gauge stays at 0 for more than N minutes, (2) anomaly — a bot's message rate drops well below its historical baseline, (3) absent-data — no telemetry from the observer itself for 15 minutes, meaning the whole pipeline (not a watched bot) has gone down.
- **Saved views:** "Currently offline bots," "Today's mod actions," "This week's quietest bot."

## 14. Verify before/while building

1. **Whether `discord.py`'s audit log method exposes what you need directly**, or whether raw REST calls are cleaner — check current `discord.py` docs for `Guild.audit_logs()`'s exact parameters before writing `audit_poll.py`.
2. **Whether Discord's gateway now pushes audit log entries directly** (`AUDIT_LOG_ENTRY_CREATE`-style event) rather than requiring polling — if it does, that's a cleaner mechanism than a 2-minute poll loop; confirm against current Discord API docs before assuming polling is the only option.
3. **Exact `discord.py` intent flag names and event handler signatures** for your installed version — these have shifted across major versions before.
4. **How many other bots your test server actually has**, and whether you have permission to see their audit-log-relevant actions — this determines how rich Day 3's dashboards look with real data.

**Already confirmed, safe to build on directly:** presence updates and bot-authored messages are visible to a bystander bot with the right (self-service, non-reviewed) intents. Interactions (slash commands) are delivered privately to their owning bot only — not a gap in this build, just why per-command latency for other bots was deliberately left out of scope in §1.

## 15. Bonus scope (only if core is done early)

Model each bot's online period as a span (start = came online, end = went offline) instead of just a gauge — turns SigNoz's trace waterfall view into a visual uptime timeline per bot, a creative reuse of a feature built for something else entirely. Track which channels each bot is most active in, not just overall volume. Terraform for the alert rules, echoing the same reproducibility story as `casting.yaml.lock`.

**Explicitly out of scope:** per-command latency for other bots' slash commands (§14), Noz (Cloud-only), RBAC.
